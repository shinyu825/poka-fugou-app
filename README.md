# ポカ富豪

ポーカーと大富豪を組み合わせたオリジナルのトランプゲームアプリです。
最初にポーカーで勝負し、その手札のまま大富豪を行い、合計ポイントで順位を決めます。
Flutter で作成しています。

## 準備

- トランプ 1 デッキ(ジョーカー 2 枚を含む 54 枚)を使用
- プレイヤーは自分を含めて 2 人
- 自分以外は CPU(難易度はスタート画面で選択)

| 難易度 | CPU の交換方法 |
| --- | --- |
| かんたん | 役に応じた定石で交換する(ペアを残して 3 枚交換、役なしなら A か K を残す など) |
| げきつよ | 山札から 4 枚多く引き、手札 9 枚の中から最強の 5 枚を選ぶ(ハンデ方式。かんたん CPU に対する勝率 約 79%) |

## 今後の対応予定

- 途中から再開する機能(スタート画面の「続きから」ボタン。大富豪の実装後に対応)
- プレイヤー人数の追加(あわせて、相手の交換枚数の表示・山札の残り枚数からの分析も実装予定)
- オンライン対戦

## ゲームの流れ

1. ポーカー
2. 大富豪(ポーカーの手札 5 枚に山札から 2 枚引いて、7 枚で対戦)
3. 2 つの合計ポイントで順位を決定

山札は 1 ゲームを通して共通です。ポーカーで手放したカード(交換の捨て札、CPU の捨て札、サドンデスで引いたカード)は、山札が尽きたときに山札へ戻してシャッフルします。大富豪で場に出したカードは戻しません。戻しても足りない場合はゲームを終了し、スタート画面に戻ります。

山札の残り枚数の例(2 人プレイ):

| タイミング | 残り枚数 |
| --- | --- |
| デッキ生成 | 54 |
| ポーカーで 5 枚ずつ配る | 44 |
| 自分 2 枚・相手 3 枚交換 | 39 |
| 大富豪で 2 枚ずつ引く | 35 |

## ポーカーのルール

- 各プレイヤーに 5 枚ずつ配る
- 交換したいカードを選んで捨て、捨てた枚数分を山札から引く(交換は 1 回のみ。交換しなくてもよい)
- その 5 枚で役の強さを比べる

役の強さと勝ったときのポイント:

| 役 | ポイント |
| --- | --- |
| 役なし(ハイカード) | 1 |
| ワンペア | 1 |
| ツーペア | 2 |
| スリーカード | 3 |
| ストレート | 4 |
| フラッシュ | 5 |
| フルハウス | 6 |
| フォーカード | 7 |
| ストレートフラッシュ | 8 |
| ロイヤルフラッシュ | 9 |
| ファイブカード(同じ数字 5 枚。ジョーカー込みでのみ成立) | 10 |

- ジョーカーはワイルドカード(どのカードの代わりにもなる)で、一番強い役になるように扱う。ジョーカー入りの役と素の役は同じ強さ
- 役がない場合は、手札で一番強いカード(A > K > Q > J > 10 > 9 ...)を持つプレイヤーの勝ち(ポイントは 1 点)
- 役の強さが同じ場合はサドンデス(引き分け時の 1 枚勝負)。山札から 1 枚ずつ引き、強いカード(ジョーカー > A > K > Q > ... > 3 > 2)を引いたほうの勝ち。決着がつくまで引き続ける
- 1 位のプレイヤーは役のポイント分プラス、最下位のプレイヤーは同じ分マイナス。中間順位は増減なし

例(4 人の場合):

| プレイヤー | 役 | 結果 |
| --- | --- | --- |
| A | スリーカード | +3 |
| B | ワンペア(KK) | 0 |
| C | ツーペア | 0 |
| D | ワンペア(JJ) | -3 |

## 大富豪のルール

ポーカーの手札はそのままに、山札から各自 2 枚引いて 7 枚にしてから始めます。
基本は通常の大富豪と同じです。

### 基本ルール

- ダイヤの 3 を持っている人から時計回り(誰も持っていない場合はランダムに決める)
- 階段なし
- 革命あり
- 縛り・数縛り・激縛りあり
- 禁止あがりあり(2・8・ジョーカーで上がるのは禁止。革命中は 3・8・ジョーカー)。スペ 3 で上がるのも禁止あがり
- ジョーカーはワイルドカード。効果のあるカードと一緒に出すと同じ効果になる(例: 7 + ジョーカーで 2 枚まで渡せる)。7 + ジョーカーのように効果カードと一緒に上がっても禁止あがりにはならない
- スペ 3(スペードの 3)はジョーカー 1 枚に対して出すことができ、出すと場が流れる

### カードの効果

6 の効果はこのゲーム独自のルールです。

| カード | 効果 |
| --- | --- |
| 5 | スキップ: 出した枚数分、プレイヤーを飛ばす |
| 6 | ドロー(オリジナル): 出した本人が、出した枚数分、山札からカードを引く。最後の手札が 6 でも引いた分が手札に残るので上がりにはならない |
| 7 | 渡し: 出した枚数まで、次のプレイヤーに手札からカードを渡せる |
| 8 | 切り: 場が流れ、出した人からもう一度始める |
| 10 | 捨て: 出した枚数まで、手札からカードを捨てられる |
| J | バック: 場が流れるまで強さの順が逆になる |
| Q | ボンバー: 出した枚数分の数字を必ず選び、その数字のカードを持つプレイヤーはそのカードを捨てる。Q とジョーカーは選べず、同じ数字を 2 回選ぶこともできない |

### ポイント

- 最後まで残ったプレイヤーの手札の枚数分、1 位はプラス、最下位はマイナス
- 他のプレイヤーが上がって場が流れ、自分の手番で残った手札が禁止あがりのカードだけの場合は、上がれないので確定負け。最下位は -10、1 位は +10
- 革命が起きた回数に応じてポイントが倍になる(1 回で 2 倍、2 回で 3 倍、3 回で 4 倍...)

例(4 人の場合、革命なし):

| プレイヤー | 順位 | 結果 |
| --- | --- | --- |
| A | 1 位 | +2 |
| B | 2 位 | 0 |
| C | 4 位(手札 2 枚残り) | -2 |
| D | 3 位 | 0 |

革命が 1 回あった場合は A が +4、C が -4 になります。

## 最終結果

ポーカーと大富豪の合計ポイントで順位を決めます。

上の例の場合:

| プレイヤー | ポーカー | 大富豪 | 合計 | 順位 |
| --- | --- | --- | --- | --- |
| A | +3 | +2 | +5 | 1 位 |
| B | 0 | 0 | 0 | 2 位 |
| C | 0 | -2 | -2 | 3 位 |
| D | -3 | 0 | -3 | 4 位 |

## 開発での AI の使い方

**仕様・ルールの設計と品質の判断は自分、実装は Claude Code が担当しています。** アプリ化(仕様の設計・開発・動作確認)は一人で行っています。

このアプリには「コードを書く AI(Claude Code)」と「ゲームの対戦相手(CPU)」の 2 つが登場するため、以下では前者を Claude Code、後者を CPU と呼び分けます。難易度(かんたん / げきつよ)はアプリ内で選べる CPU の強さです。

### 自分が担当したこと

- ゲームルールの設計(友人との遊びの中で生まれたルールで、大部分は自分が発案し、みんなで遊びながら調整。ポーカーと大富豪の組み合わせ、ポイント制、カード効果、禁止あがり、山札の扱い)
- 仕様の決定(難易度を選択式ボタンにする、サドンデスの流れとボタン文言、ポイントの反映タイミング、大富豪画面のボタン配置とカード選択の仕様)
- 「げきつよ」CPU の方式の考案と難易度調整(下記「げきつよ CPU ができるまで」を参照)
- ジョーカー導入の判断と細かいルール(ファイブカードを最強役にする、ジョーカー入りと素の役は同じ強さ、サドンデスではジョーカーを最強にする)
- 実機・シミュレータでの動作確認とバグ報告(手札の並び順、画面を戻ったときの手札の持ち越し、大富豪で相手だけ枚数が増える、ポイントが先に反映される など)
- コードレビュー(MVVM の責務分離を確認し、ダイアログ表示が ViewModel と通信層にある点、使われていない ViewModel が生成されている点、端末保存を ViewModel が直接触っている点の整理を指示)

### Claude Code に任せたこと

- コードの実装、バグの原因調査と修正
- CPU 同士の対戦シミュレーションによる強さの計測(計測によって 1,000〜2 万回対戦)
- ユニットテストの作成
- MVVM の整理(ViewModel と通信層からダイアログ表示を分離、端末保存を Repository に移動、ゲーム状態を `GameState` に切り出し、通信をテストで差し替え可能に)
- 開発環境の更新(iOS の Swift Package Manager 移行と CocoaPods 除去、Android の Gradle / Kotlin 更新)
- README とコメントの文章化

### げきつよ CPU ができるまで

Claude Code が最初に実装したのは、モンテカルロ法で「どのカードを捨てれば平均的に強くなるか」を計算する CPU でした。しかし、かんたん CPU と 1,000 回対戦させても勝率は約 50% で差が出ませんでした。続いて相手の手札を参照して勝てる確率が最大になる交換を選ぶ方式も試しましたが、約 52% とほぼ効果がありませんでした。

原因は「交換が 1 回だけ」というルールにあります。1 回の交換で逆転できる幅は小さく、考え方をどれだけ工夫しても、かんたん CPU の定石(ペアを残して 3 枚交換)とほぼ同じ判断になってしまうためです。

そこで自分で、考え方ではなく使える手札の量に差をつける方式を考案しました。CPU はカードを捨てる代わりに山札から数枚引き、元の手札と合わせた中から最強の 5 枚を選ぶハンデ方式です。Claude Code に対戦シミュレーションを実行させ、追加で引く枚数ごとの勝率(2 枚: 約 55%、3 枚: 約 68%、4 枚: 約 79%、5 枚: 約 86%)を見ながら、「強いが勝てることもある」4 枚に決めました。

### Claude Code の提案を採用しなかった箇所

- **モンテカルロ法の CPU**: 上記の通り、計測で差が出なかったため不採用
- **「かんたん」を強化版に昇格し、より弱い CPU を新設する**: 差を確実につけるための代替案だったが、本当に強い CPU を作る方向を選んだ
- **ポーカー画面に入ったら自動でカードを配る**: 「カードドロー」ボタンを押す操作は残したかったので不採用
- **相手の交換枚数を画面に表示する**: 表示するのではなく、山札の残り枚数から自分で推測できる要素として残すことにした(人数を増やすときに検討)

### Claude Code の指摘で方針を変えた箇所

- **画像の読み込み失敗時にカードを引き直す**: 自分の案だったが、Claude Code から「引き直すと山札が減って手札も変わる」と指摘され、画像だけ再読み込みする方式に変更した

## 技術構成

- Flutter / Dart(iOS / Android 向け。デスクトップ・Web 用のフォルダは削除済み)
- 状態管理: provider
- 通信: dio
- 画像キャッシュ: cached_network_image
- トランプのデッキ・画像: [Deck of Cards API](https://deckofcardsapi.com/)

## ディレクトリ構成

```
lib/
├── constants/    文言・役・難易度の定義
├── models/       役判定、CPU の思考、カード、API レスポンス、ゲーム状態
├── repository/   API 通信、端末保存、リクエスト定義
├── view_models/  画面の状態とロジック(MVVM の ViewModel)
└── views/        画面、UI 部品、ダイアログ
test/             ユニットテスト(役判定、CPU の思考、並び順、ポーカーの進行)
```
